# Профили сотрудников и сервер проверки

## Состояние

Профили и история используют действующий Supabase-проект сайта. Схема применена, RLS проверена, руководитель назначен отдельной записью в `cqa_managers`. Секретов и персональных адресов руководителя в репозитории нет.

Оценщик ИИ и транскрипция остаются за серверной частью, которую подключают отдельно. Код API-маршрутов не изменён. `src/qa-app.tsx` после успешного `requestAnalysis` помечает источник как `ai`; JSON формата оценок остаётся прежним.

## Поток в интерфейсе

1. Руководитель загружает разговоры в «Проверку».
2. Автор определяется по представлению **оператора**, с привязкой к ID реплик. Реплики клиента и сообщения с неизвестной ролью не используются.
3. Известный единственный вариант имени связывается с профилем; новое имя создаёт профиль при сохранении. Совпадения нескольких профилей и смена операторов требуют ручного уточнения. Два человека с одинаковым первым именем не должны автоматически объединяться: заведите полные имена и проверенные варианты в профилях.
4. «Распределить разговоры» сохраняет набор; карточка разговора позволяет выбрать сотрудника вручную и сохранить отдельно.
5. Руководитель связывает профиль с email уже зарегистрированного аккаунта. Сотрудник после входа открывает «Рабочий профиль», видит свои разговоры, критерии и доказательства.
6. Сотрудник подаёт апелляцию на критерий конкретного разговора. Руководитель принимает с новой оценкой или отклоняет с причиной.

Учебный пример находится отдельно, не отправляется в БД и не попадает в настоящие рейтинги.

## Таблицы

- `cqa_managers(user_id)` — доверенные руководители. Клиент не может добавлять записи.
- `cqa_employees(id, name, aliases, user_id, account_email)` — профили; имя само по себе не даёт доступ к аккаунту.
- `cqa_conversations` — разговор, назначенный сотрудник, транскрипт, снимок чек-листа, исходные оценки и история решений.
- `cqa_appeals` — автор, критерий, комментарий, статус, причина и время решения.
- `cqa_employee_ratings` — представление `security_invoker`: видит только разрешённые RLS строки.

`score` в разговоре — вычисляемое поле. Не передавайте его в INSERT/UPDATE. Расчёт выполняет `cqa_review_score(checklist,evaluations)`: шкалы, веса, N/A, последние решения по апелляциям. Неполная оценка даёт NULL. Рейтинг сотрудника = AVG(score) / 20, без разговоров с NULL; ноль — настоящая оценка, а не отсутствие данных.

## Как сервер ИИ сохраняет результат

Сервер сначала проверяет аккаунт и право руководителя. Можно использовать его JWT с RLS либо серверный service role после собственной проверки доступа. Секретный ключ никогда не попадает в браузер.

```ts
// Служебный фрагмент; db — уже авторизованный клиент, employeeId подтверждён.
await db.from('cqa_conversations').insert({
  employee_id: employeeId,
  fingerprint, // SHA-256 JSON [sourceId ?? null, channel, transcript.map(t=>[t.timestamp,t.speaker,t.text])]
  source_id: sourceId,
  name, language, channel, transcript,
  checklist, // снимок критериев этой проверки
  evaluations, // {criterionId: {value, reason, evidence:[turnId], appeals:[]}}
  assignment_evidence: operatorIntroductionTurnIds,
  review_source: 'ai'
});
```

Поле `fingerprint` уникально: повторная загрузка не добавляет второй балл. Для обновления используйте `id` + текущую `version`; триггер увеличивает версию. Не перезаписывайте чужие решения старым результатом оценщика. Готовая клиентская реализация — `saveReview` в `src/workforce-client.ts`.

Имена ИИ являются кандидатами, а не идентификатором доступа. Сопоставляйте с `name/aliases`, неоднозначные случаи оставляйте без владельца до решения руководителя. Не выбирайте первый результат при нескольких совпадениях.

Аудио не хранится в этих таблицах: сохраняется транскрипт и канал разговора. Если добавляете записи, используйте приватное хранилище и короткоживущие ссылки с тем же контролем владельца. Не сохраняйте object URL браузера как постоянную ссылку.

## Апелляции и доступ

Сотруднику разрешены SELECT собственных строк и INSERT своей апелляции на собственный разговор. Он не может менять оценки, владельца, профиль аккаунта или решение. RLS ограничивает данные в БД, а не только в интерфейсе.

`cqa_link_employee(p_employee_id,p_email)` проверяет роль руководителя, находит существующий аккаунт и связывает UID. Узкая привилегированная функция находится в `cqa_private`, проверяет auth.uid(), использует пустой search_path и недоступна anon.

`cqa_resolve_appeal(p_id,p_status,p_value,p_reason)` работает транзакционно, проверяет руководителя, блокирует строки, сохраняет исходное `value` и добавляет решение в `evaluations[criterionId].appeals`. Новые score и звёзды вычисляются автоматически. Обязательна причина.

Начальное назначение руководителя выполняет администратор БД по проверенному UID зарегистрированного аккаунта, а не по пользовательской метадате. Самостоятельного назначения через форму нет.

## Проверки

- `npm test` — прежние CQA проверки плюс распознавание RU/KZ/EN, клиентские цитаты, неоднозначные имена, шкала звёзд, NULL, fingerprint и апелляции.
- `supabase/tests/workforce_rls.sql` — транзакционный тест с ROLLBACK: изоляция двух сотрудников, запрет чтения чужого разговора и изменения оценки, запрет самоназначения руководителя, апелляция только своего разговора, решение руководителя, сохранение исходного балла, пересчёт звёзд, запрет anon. Тестовые аккаунты не остаются в БД.
- Схема: `supabase/migrations/20261107174942_employee_profiles_and_review_history.sql`.

Рабочие черновики руководителя не пишутся в общий localStorage: постоянная история сохраняется через «Сохранить в профиль» / «Распределить разговоры». Обычному сотруднику страница проверки показывает переход в личный профиль; загрузка общего набора доступна руководителю. Гостевой учебный режим отделён от рабочих аккаунтов.
